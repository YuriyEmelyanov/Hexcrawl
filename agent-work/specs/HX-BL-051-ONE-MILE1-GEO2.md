## Data contract and reproducibility

Build a pure immutable `GeometryPlan` from accepted source map + physicalGrid + owner/river/route refs + explicit authored sizes. It returns either a complete validated candidate and changes, `unchanged`, or a structured error with entity refs. It must never mutate input, consume global world RNG, generate a region, or partially commit.

Stable keys use source riverID plus canonical source edge/node keys, POIentityID and road/segment/crossing keys, never array index, label, camera, rounded SVG pixel coordinates or iteration order. Use actual grid integer vertices: `(2q+r+cx,3r+cy)`, corners `(1,-1),(1,1),(0,2),(-1,1),(-1,-1),(0,-2)`; world `(origin.x+vx/2,origin.y+vy/(2√3))` miles. Edge key is numerically lexicographically ordered endpoint pair. This matches detailGrid; do not use current display `.001` rounded edge keys as new vertex topology.

`algorithmVersion=geo2-v1`. For an unconstrained left/right decision hash UTF-8 JSON array `["geo2-v1",worldSeed,riverId,canonicalSourceEdgeKey,cellQ,cellR]` with unsigned FNV-1a32 (initial2166136261, byte xor then Math.imul16777619, unsigned). Even=left, odd=right relative to the **stored upstream→downstream** direction. This is a deterministic pseudo-random tie-break, not cryptographic randomness. Reversing source array order or editing names does not change it. Persist chosen side and actual resulting routes; load validates them without rerouting. If preferred side is blocked, use the other legal side and record constraint fallback. If both are blocked, fail the plan atomically, never draw a center shortcut. No “reroll refinement” control in GEO2.

Candidate records: source revision/fingerprint and algorithmVersion; fine river records `(sourceRiverId,sourceEdgeKey,ordered integer-edge subpaths,endpoint/junction refs,F)`; crossing records `(sourceCrossingKey,source river/road refs,kind,finePoint,tangent)`; POI records `(poiId,parent6,old/new anchor,footprint,water contact,route entries,provenance)`; road records `(sourceRoadId,sourceSegmentKey,ordered fine polyline,access/crossing refs)`; lake mouth records `(sourceRiverId,lakeId,mode,shore contour signature,contact)`. Source values/provenance are preserved. Render pieces are not new game entities. Persist model coordinates, not screen paths or cached SVG. sourceFingerprint covers only relevant source geometry, IDs/incidence/F, water contours, requirement refs and extent/lock inputs, in canonical order; excludes names/notes/UI/camera/locale and global RNG continuation state. A name edit must not invalidate or reroute geometry.

## River paths, connectivity and lake boundary

1. Enumerate source directed graph, class F, actual shared junctions and terminals. Map each shared junction once to the nearest legal fine vertex using world-distance then numeric vertex-key ties; distinct source junctions must not collapse. Terminals can be interior points of fine edges (split that edge at a terminal). Keep source-to-fine correspondence for every segment. Never route independent copies of the same junction.
2. Build a finite graph of fine edges covering cells intersected by the source segment plus one adjacent-cell ring, clipped to existing generated geography. Do not extend the generated map. Prefer the two perimeter chains around each cell crossed by the source chord, with the same entry/exit ports; endpoints/junction connectors use the same edge graph. For a diameter through a cell center these are its left/right three-edge chains. Shared ports must be reused across successive cells; arbitrary independent left/right polylines are not allowed to leave gaps.
3. Choose a connected directed edge chain within that corridor satisfying terminals/junctions, with the above side tie-break. Constraint order: valid topology/shore/ownership first; minimum number of edge steps second; minimum summed squared distance of edge midpoints to source segment third; preferred side then numeric edge sequence ties. A search implementation may use dynamic programming or constrained graph search; it must return the same canonical result irrespective of input-array order. Bound search to this finite corridor; exhaustion returns `route_conflict`, not fallback drawing. The implementation supplies the finite work bound and records it in evidence; no new product-scale benchmark is authorized.
4. Do not introduce new river crossings, loops, disconnected components, overlaps/unions or confluences absent in the source graph, even between parts of the same river. Existing confluences remain shared nodes, maxdegree3 per RIV-006. F/source direction/rapid/waterfall identity unchanged; marks relocate onto their linked segment at preserved normalized arc position, with their physical direction checked. Source boundary exits remain continuable; any displaced fine boundary port retains its source exit ref. Constraint conflicts reject the candidate with concrete refs rather than silently suppress a river.
5. Preserve WR1 visible width function and classes; no /6 shrink and no claim that legacyF1=.45mile is physically approved. At corners use the actual finite joined stroke envelope (round joins/caps, clipped at water body), not an infinite straight-line `width/sin(angle)` approximation.
6. **C06:** for every river/lake incidence derive the actual visible shoreline for the selected mode: union of lake hex polygons for Tiles/Emoji, seeded basin contour for Color (including islands). Find the first intersection of the last routed water corridor with that contour on the correct inlet/outlet component. End visible river water at that contact; clip all underwater center connector paint by the lake body. Land-side axis must remain on fine edges; no extra dry-land segment to lake center. Lake-renderer-owned blend under water is allowed, not a new land river axis. Lake IDs/cells/seeded shape/inlet direction remain. For a mode/rotation where there is no valid shore contact the **entire plan** fails `mouth_conflict`; changing rendering style must never commit a broken mouth. Validate all three modes before enabling Apply; previews retain the same accepted topology.

## POI, crossings and roads

Only an explicit river requirement with known provenance and resolvable stable river ref makes a POI eligible for automatic movement. Existing water attachment is evidence, not an excuse to invent a requirement; use existing POI rule/requirement lookup. Missing provenance is `unknown` and is listed as unresolved in preview, never treated as “requires river” or “no requirement”. The disputed catalogue-town example remains unknown, no automatic move of all towns. A known requirement whose river ref is missing is an error; an unknown requirement does not block unrelated valid refinement but cannot be reported as C03 solved.

For an eligible POI enumerate legal anchors/footprints **inside its same source6mile parent**; choose minimum displacement from old anchor satisfying river-bank contact and current land/POI placement rules; ties by integer cell then coordinate. For marker use bank contact as anchor. For one/multicell footprint require a designated entrance/contact on the river-facing part of the actual footprint boundary or within its physical contour; do not accept merely the same coarse parent or measure to the river centerline. Keep existing bank side if known; do not move a POI across its river just to shorten displacement. Unknown side may use nearest legal bank. Preserve existing extent/provenance/connected footprint and count, translate conditional/manual extents rigidly where legal; never shrink a footprint to fit. Measured georeferenced polygons and explicit locked authored anchors are not auto-translated: report conflict requiring user action in existing editor, with no losing override. No legal same-parent placement → `poi_conflict`, plan unchanged. A user-supplied multi-mile settlement remains multi-cell; no new town catalogue accepted.

Relocate every old crossing to the nearest valid transverse intersection of its refined river and adapted road, retaining key/kind/river/road references and required graph incidence. No newly untyped road/water intersection or road along water is allowed. Crossing at a corner requires actual finite water-envelope clipping, no assumption of perpendicular midpoint. Preserve ordered crossings along a road; multiple crossings must not swap or collapse. All old7 must survive. Use existing ROAD-10 admissibility of F/kind; do not downgrade bridge/ford/ferry or recalculate kind from new geometry.

Recompute only road portions linked to a moved POI or moved crossing; preserve other segments/source-road IDs, destinations, road/trail class, names, entrances and boundary-exit refs. Route from each unchanged network junction/exit to new designated POI entry/crossing along legal land geometry. Use G2-R-ROAD-LENGTH: physical route length first, old-route deviation only for equal-length legal routes, canonical numeric path keys last (defined below); no new road-generation count or terrain preference. Connecting one approach must not sever another approach of the same POI. If a legal path needs an unapproved new crossing, fail `road_conflict`. Data retains continuous path into/through the POI. Paint is clipped inside the **union of cells for one-cell-or-larger footprint**; marker-only POI does not trigger this mask. Shared internal cell boundaries are not road gaps; holes in a multi-cell outline do not count as POI land unless occupied. Apply same geometric clipping to road strokes, dash pieces and bridge rails in map/PNG, preserving visible water/type semantics at actual crossings. Do not delete hidden road entities or use camera-size icons as the mask. Editing/hit targets must still reach the POI and show its real connected route in its existing card.

## G2-R-ROAD-LENGTH — admissible routes and objective

Only the affected road portions already selected by dependency closure are eligible for optimization. Preserve fixed source-network endpoints, designated new POI entries, every approach, crossing identity/kind/order and the crossing-placement constraints above. Do not change the prior minimum-displacement POI placement rule to shorten roads. Hide paint inside POI footprints without removing that part from the data route or its length.

For each legal candidate polyline P in model world coordinates measured in miles, L(P)=sum hypot(x[i+1]-x[i],y[i+1]-y[i]). Use full-precision model coordinates, not SVG/camera pixels, rounded display distances, edge count, travel cost or biome weight. Remove duplicate consecutive points. Length is primary; a path with smaller deviation or fewer vertices cannot beat a shorter legal path.

For equal lengths use mean squared distance from candidate to the original affected source polyline, integrated over normalized candidate arc length t∈[0,1]: D(P)=∫dist(P(t),P_old)^2 dt. This secondary metric does not penalize unrelated roads or change source-generation rules. Then compare canonical numeric coordinate/key sequences in source road direction, never locale/array order. Numerically equal means difference ≤1e-9 mile for L and ≤1e-9 square mile for D; this is numerical precision, not a new user distance setting. Evidence must record the compared objective values and tolerance; no display rounding before comparison.

Search legal land within existing generated geography, without extending the world or inventing crossings. A finite candidate graph/search domain and work/cancellation bound are implementation details, but must be documented and sufficient to compare the competing legal paths. A single straight candidate and a locally shortest path in an arbitrarily pruned corridor do not demonstrate this requirement. A bounded search that exhausts its work budget must explicitly report incomplete search, not claim no legal route or shortest route. Do not silently keep a known longer path when a shorter admissible candidate exists. Return atomic structured failure with affected refs on budget/cancel/conflict; no partial route acceptance. Implementation evidence must distinguish search limitations from proven topological conflict.

**G206-LENGTH acceptance witness (synthetic, miles, not an actual-map measurement).** Old affected route A(0,0)→(0,1)→oldPOI(4,1). The eligible POI has moved to B(4,0), on dry legal land in the same parent. Candidate P_long=A→(0,1)→(4,1)→B has L=6 and stays closer to the old route. Candidate P_short=A→B has L=4 and is legal. Select P_short even though its deviation is greater. Preserve a second approach to that POI independently; do not collapse it. For equal-length legal routes A→(2,1)→B and A→(2,-1)→B (both sqrt20), select the smaller D; if D also equal, numeric key tie. Reordering source arrays gives the same result. Separate G205-CONSTRAINT variants make the nominally short route illegal (untyped water/new crossing or missing approach): reject that candidate and choose a legal alternative or fail atomically. These examples specify observable acceptance, not newly added permanent tests; programmer first checks existing coverage.
