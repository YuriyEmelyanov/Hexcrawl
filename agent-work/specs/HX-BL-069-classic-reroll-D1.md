# HX-BL-069 · Переброс последнего региона Classic
Черновик D1 для интервью. Старт согласован в [реестре решений](../approvals.json). Следующий исполнитель — интервьюер. Для разработки нужна чистовая версия после интервью.

## Пользовательский результат
Мастер правит первый регион, затем подбирает другой вариант последнего. Первый регион сохраняет авторское состояние, последний получает новый вариант. Используются существующая команда, существующий редактор и формат открытия карты. Новых элементов интерфейса нет. Произвольное выделение области и закрепление внутри неё относятся к HX-BL-075.

## Поведение
1. За точку сравнения взять карту непосредственно перед нажатием, включая изменения, сделанные после создания последнего региона. Исторический снимок до создания региона годится для генерации, но может содержать устаревший внешний мир.
2. Определить область заменяемого региона по его принадлежности на исходной карте. Близость к границе сама по себе не разрешает изменять внешнюю клетку. Изменившийся контур не должен поглотить уже занятую клетку соседнего региона.
3. Сохранить во внешних клетках ручной биом, авторские поля карточки и заметки. Для внешних POI сохранить существование, тип, положение, название и заполненные пользователем поля, поддерживаемые исходной версией. Это распространяется на создание, переименование, перемещение между внешними клетками и удаление. Удалённое после создания последнего региона место должно остаться удалённым. Полностью внешние дороги, водные объекты и ручные элементы их геометрии сохраняют связи и положение в той мере, в какой текущий редактор позволяет их менять.
4. Внутри заменяемого региона применяются обычные правила переброса. Защита пересекающего границу объекта требует отдельного решения ниже. Запись полурезультата запрещена. Для конфликта предложен отменяемый исход с полной сохранностью карты и понятной причиной через существующую обратную связь.
5. Успешный переброс — одно действие в истории. Отмена возвращает исходную карту с авторскими правками и прежним вторым регионом. Повтор возвращает именно уже полученный вариант. При повторном импорте JSON сравнить содержимое карты, включая удаления и привязки. Сохранение стека отмены между сессиями в задачу не входит.
6. Если на исходной карте команда недоступна, сохраняются существующие условия доступности. Для старых сохранений без необходимой истории нельзя реконструировать авторские правки по догадке. Не менять поведение прочих профилей, обычного создания и удаления региона.

**Совместимость старых карт (AC5).** Сразу после открытия проверенных карт v2 история генерации пуста. После создания нового региона в той же сессии проверяется обычная защита внешних правок. Если команда доступна, но область замены нельзя надёжно восстановить, сохранить исходную карту и сообщить мастеру причину. Это условие уже разобрано интервьюером в разделе `coverage.AC5` первого раунда.

## Влияние на оценку и передача
В модели 1.3-rc8 строка [SEED-07](../score/rules/S02-C01.md) имеет 0 из 10 по таблице строки. Условный остаток +1,48 L1. Доказательства — AC1–AC5 с внешними правками до и после. В [RER-16](../score/rules/S03-C02.md) принято 1,2 из 2,4 за новый вариант. За сохранение внешних правок возможны ещё 1,2 веса, или +0,59 L1. Для этой строки отдельно зафиксировать изменение второго региона и равенство авторских данных первого после загрузки. Потолок двух строк +2,07 L1. Общую строку RER-16 с HX-BL-075 учитывать один раз. Влияние на L2/L3 неизвестно. Для SEED-07 источник исходной оценки — таблица S02-C01 на PR №511, опубликованный SHA `7ecf76c5c71724e1d810ba34480e4962c98b444e`. Наблюдения D1 и проверка RER-16 на пяти картах относятся к последующему выпуску PR №510, SHA `b887422b6b05663124f0ce431953f863350e4a86`. Проверяющий закрыл оба события публикации по 1.3-rc8: [PR №511](../results/2026-11-21T1658-reviewer-PR511-closure.json) и [PR №510](../results/2026-11-21-reviewer-PR510-publication.json). Предварительный расчёт проверяющего при приёмке, окончательный после сверки публикации.

Интервьюеру проверить весь D1, включая границы перечня внешних правок и варианты на стыке. Ответы привязать к AC2–AC4 по таблице развилок. AC1 и AC5 проверяются независимо. Затем аналитик уточняет требования и передаёт чистовую версию программисту. Ориентир из утверждённого предложения — 6–10 запусков на весь путь при одном цикле исправлений, ожидание решений отдельно.
