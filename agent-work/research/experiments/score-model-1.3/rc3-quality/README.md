# HexCrawl 1.3.0-rc3 · приёмка и лидерство

Предложение владельцу **HX-SCORE-1.3.0-rc3**, awaiting_owner_approval. Оценивается приложение. Источник перечней игр — действующие сценарные когорты версии 2026-11-15-ranking1.4-CROWS-addition. Изменения состава аудитории и рыночных весов требуют отдельного решения. Релиз для первого расчёта — d6daa2cdbc1c17b942d51fe050fac51752cf9fee (PR 509).

## Что показывает один уровень

| Уровень | Общая часть | Игровая часть |
|---|---|---|
| L1 · подготовка карты | Генерация, карты разных масштабов, редактирование, экспорт и возврат к своей работе | Принятые операции каждой игры из top20 create |
| L2 · ведение | Навигация, сохранность карты и состояния экспедиции, время, маршрут, видимость для игроков | Отдельные top20 play_now и применимые правила ведения |
| L3 · сопутствующие механики | Обмен с внешней системой и сохранность возвращённого изменения | Расчёт открыт до определения корпуса и когорты |

Для каждого уровня публикуются две шкалы до 1000 и один показатель до 1000. Предлагаемая формула уровня — половина общей части плюс половина игровой. Приоритет работы — L1, затем L2, затем L3. В уровне сначала рассматривается применимое из top5, далее top10 и top20. Ранг помогает выбрать следующую работу. Слот каждой игры стоит одинаковые 50 игровых баллов, поэтому менее популярную игру нельзя заменить дополнительными правилами фаворита. Каждый уровень имеет собственный знаменатель. Сквозной тест хранится один раз, применяется на релевантных уровнях; суммы уровней между собой не складываются.

## Когда функция закрыта

1. До реализации аналитик записывает действие мастера, исходную карту, адресуемый объект, ожидаемый результат и независимые данные, которые должны сохраниться. Для составного правила закрепляет исчерпывающие случаи и их ID. Наименование поля в интерфейсе не служит приёмкой.
2. Для интерактивного действия назначается профиль generate/edit/read/transfer/session. Приёмщик фиксирует путь исполнения и хранения, тип отрисовки, режим, число гексов до и после, состав карты, устройство/ОС/браузер, холодный или прогретый запуск и точный SHA. Финиш замера — видимый результат, с которым мастер уже может работать. Таймер обработчика и время CI отдельно.
3. Проверяются результат, целостность, а для изменений — сохранение и повторное открытие. Проверяются ошибки и отмена, когда они входят в операцию. Ошибка или потеря данных закрывает возможность засчитать затронутый случай. Для критической потери ставится также блокировка заявления о лидерстве.
4. Для профиля генерации действуют унаследованные строгие пределы P95 < 1,5 с на эталонном ПК и < 3 с на среднем Android. В rc3 предложены минимум 20 запусков на каждый тип устройства и предел < 10 с на **каждый** запуск. Таймаут входит в выборку. Даже один результат за 50 минут проваливает случай на этом устройстве, в том числе если остальные 19 запусков быстрые. Остальные бюджеты предложены в catalog.json; до испытаний фиксируются конкретные устройства и нагрузки N. Одно успешное N даёт результат только для этой нагрузки.
5. Приёмщик записывает pass/fail/unknown по случаю и устройству, ссылку на воспроизводимое доказательство и версию продукта. Для интерактивной матрицы desktop и Android имеют по половине веса случая. Полученный на ПК результат даёт частичную приёмку при открытом Android. Полное закрытие требует всех применимых случаев. Неизвестное расширяет интервал. Измеренные отказы снижают верхнюю границу. Контрпример имеет приоритет над отсутствующим замером для той же ячейки.

### Где заканчивается ядро и начинается игра

**S03-C01, общий редактор.** Мастер меняет биом у выбранного гекса. Проверяем адрес, изменённый биом, сохранение соседних объектов и повторное открытие. Отдельные операции — правки POI, воды и принадлежности региону. Базовые, граничные и мигрированные данные, различные реализации редактора и сохранения образуют матрицу ядра. Разные названия игр поверх одного пути не размножают эту матрицу. Поля и ступени G1–G4 зафиксированы в catalog.json.

**PF2-RM-044-L1-v2, профиль PF2.** После редактирования гекс должен одновременно сохранить горный рельеф и снежный тип местности. Подмена горы снежной равниной провалит правило даже при исправном общем редакторе. Для игрового балла понадобится локальное доказательство смысла правила. Снова измерять одинаковый путь на 20 названиях игр не требуется. Проверяемый механизм timing_ref переиспользует измерение только при совпадении SHA, операции, нагрузки, отрисовки и хранения. Для иного адаптера, масштаба или режима с иным путём нужна собственная проверка. Приёмщик отвечает за обоснование эквивалентности. В игровую строку не наследуется правильность игрового результата.

## Как считаются баллы

* В catalog.json сохранены все 50 исходных ID, весов и целей G4 версии 1.2. 40 критериев распределены по общим возможностям, пять S10 образуют отдельную проверку лидерства. По пяти исходным целям о ситуациях, историях, встречах и фракциях требуется решение о применимой части. Они сохранены с причиной и блокируют окончательную сертификацию соответствующего уровня. Утверждённые ранее задачи сохраняют свои решения.
* Общая часть уровня — 1000 × сумма (вес критерия × принятая доля) / сумма применимых весов. Первая четверть критерия распределяется между зарегистрированными прототипными операциями. Последующие ступени 0,50 / 0,75 / 1 требуют соответственно подтверждения обычного рабочего сценария, матрицы ошибок с CI и пользователями, полной исходной цели и сравнения. Для проверки чисто технического инварианта применяются собственные доказательства. Искусственный таймер на branch coverage не нужен. Область каждого такого доказательства видна в observations.json.
* Игровая часть — сумма по 20 играм (50 × средняя принятая доля правил игры). Доля правила — среднее устойчивых приёмочных случаев, с учётом устройств. Пустой корпус даёт интервал 0–50, полная поддержка требует закрытого корпуса. Правила вне сценарного top20 видны в game_rows и могут быть проверены независимо. Предварительный показатель из rc2 оставлен видимым. Его половинный вес неразложенного статуса partial — наследованное приближение; в принятом результате нужны конкретные случаи.
* Пример на фиксированном знаменателе. При 29 строках PF2 одно полностью принятое правило даёт 50/29 = 1,7241 балла игровой части L1 или 25/29 = 0,8621 общего показателя L1. Прохождение только настольного случая даёт 0,4310 балла L1. Калькулятор считает без округления; отображение округляется в самом конце.
* Порог лидерства — минимум 950 на уровне, минимум 80% в каждом применимом блоке, минимум 60/70 внешних баллов S10, закрытые корпуса и полная поддержка 20 игр, отсутствие критических дефектов, внешнее сравнение на данном сценарии. Сохраняются входящие в цели S10 требования к конкурентам, слепому исследованию мастеров, реальному использованию, сообществу и публикации. Скорость команды или число закрытых PR не заменяют эти доказательства.

| Сценарий | Функциональное свидетельство по игровым правилам (rc2, из 1000) | Игры с инвентарём | Подтверждённый минимум общей части | Подтверждённый минимум игры с новыми проверками | Минимум уровня |
|---|---:|---:|---:|---:|---:|
| L1 create | 298,44 | 12/20 | 11,11 | 0 | 5,56 |
| L2 play_now | 4,79 | 10/20 | 15,31 | 0 | 7,65 |

Здесь подтверждённый минимум отражает наличие подходящих доказательств. Он пока непригоден для вывода, что ведение опережает создание. У общей части разные знаменатели (675 и 490), квалифицированные наблюдения пока покрывают CI на принятом дереве и сохранность данных на одном образце; в обоих случаях зачтена только прототипная ступень. Уровень L3 и рыночное лидерство открыты. Полный JSON показывает исходные функциональные статусы и интервал приёмки для всех 304 строк (155 L1, 149 L2) зафиксированного инвентаря. Новые строки последующих ревизий добавляются отдельной версией.

На PR 509 приёмка релиза задокументировала пользовательский редактор, отмену и повтор правки и JSON. В этой ревизии повторно проверена строка PF2 на действительных обработчиках продукта. В 20 повторах фиксированной карты после замены биома в 2,0 и повторного импорта совпали карта целиком, остальные объекты и состояние генератора. Сохранились height=3, mountains и snow_ice. Результат с сырыми замерами — edit-result.json; P95 обработчика с формированием документа около 4,25 мс. Замер до готового экрана на обоих эталонах остаётся открытым. Локальный Chromium остановился до первого UI-замера с “socket() failed: Operation not permitted (1)”. Скрипт probe.mjs приложен как заготовка прогона на разрешённом браузерном стенде; синтетические прогоны test.mjs в баллы не попадают.

## Десять PR и расширение модели

В report.json для каждого PR сохранены parent/merge, предмет изменения и дельты функциональных результатов для ядра и игры. По девяти PR нет сопоставимой пары замеров обязательного качества до/после. По PR 508 менялся только таймаут сборки Pages, вклад в оцениваемые операции приложения равен нулю. PR 509 дал функциональное свидетельство по снежным горам PF2 (+1,7241 на игровой шкале L1); приёмочная дельта ждёт скорости взаимодействия. Изменение уверенности при новой проверке уже выпущенной функции фиксируется как прирост доказанности на прежнем SHA.

Для добавления масштаба 60 миль дополняется перечень случаев physical-grid, рядом с 1, 6, 12 и 24. Для плавного поворота реки и дороги предусмотрены самостоятельные случаи двух соответствующих критериев; проверяются непрерывность русла/дороги, переправа и сохранение правки. Если меняется состав или вес, фиксируются версия, мотив и сравнение старого и нового каталогов **на одном релизе**. Затем два релиза сравниваются на **одном каталоге**. Первое число характеризует изменение цели, второе — изменение продукта. Новая строка проходит согласование перед попаданием в действующую численную методику. На текущих двух частях даже при принятии всех уже известных игровых результатов 40/60 вместо 50/50 придало бы больший вес играм; с нынешним малым объёмом квалифицированных доказательств минимум L1 составил бы 4,44, при 60/40 — 6,67. Состав игровых когорт от смеси не зависит.

**Ближайшая проверка для приёмщика** — тот же опубликованный релиз, фиксированные карты и реальные устройства. Измерить от выбора нового биома до появления результата на карте, экспортировать, открыть заново, сверить редактированный гекс и остальную карту. Для генерации отдельно измерить от команды до видимого редактируемого региона, с числом гексов, ошибками и таймаутами по каждому запуску. Это позволяет квалифицировать уже найденную функциональность без новой продуктовой разработки.

## Воспроизведение

Из этого каталога при наличии дерева agent-operations: `node test.mjs`, `node score.mjs > report.json`. Для независимой проверки продукта на Node 24: `node edit-probe.mjs /path/to/product-checkout` с зависимостями проекта. Проверяются Git blob SHA всех исходников и двух задействованных помощников. Для браузерного прогона нужен запущенный локальный production build, Playwright и Chromium; `PROBE_URL=http://127.0.0.1:18377 node probe.mjs`. Обработчик на CPU не подменяет время пользовательского сценария.
