# Операционный процесс четырёх ролей
Действует по прямому решению владельца от 24.10.2026, записанному в текущем чате команды. Имеет приоритет над прежними расписанием и бюджетными блокировками в AGENTS/vision/плане23.10. Main этим документом не изменяется.

Каждый час, Europe/Moscow. Решение владельца от 24.10.2026: роль выбирается по состоянию утверждённой очереди, прежняя привязка ролей к часам отменена.

Выбирай роль по актуальному состоянию утверждённой очереди в GitHub, а не по часу запуска. Почасовой запуск — только проверка готовности работы, не обязательная смена роли.
Приоритет выбора:
1. Явное актуальное поручение владельца задаёт роль и задачу.
2. Если есть незавершённый активный claim, не дублируй работу; продолжай только собственный безопасно восстановленный запуск либо возьми другую готовую утверждённую задачу своей роли. Устаревший lease сам по себе не доказывает завершение.
3. Есть замечания проверяющего по утверждённой задаче — программист исправляет их; затем продолжает незавершённую реализацию либо берёт утверждённую задачу с готовой спецификацией.
4. Есть review_ready с конкретным SHA и необходимыми проверками — проверяющий независимо проверяет этот SHA.
5. Есть утверждённая задача без пригодной спецификации либо противоречия в ней — бизнес-аналитик.
6. Есть явное разрешение владельца на выпуск конкретного принятого пакета — программист выпускает только этот проверенный пакет, проверяя совпадение SHA и разрешения.
7. После выпуска с score_update_pending — стратег-менеджер завершает обновление оценки по разделу ниже; при отсутствии score_assessment направляет ограниченную проверку проверяющему. Это обязательный этап и не ждёт суточного итога. После пересчёта в том же запуске предложи следующую продуктовую задачу по разделу ниже.
8. Если готовой исполнительской работы и актуального предложения следующей задачи нет — стратег готовит такое предложение по разделу ниже. Если появились новые решения, результаты, обратная связь или нужен очередной суточный итог — стратег-менеджер координирует очередь и готовит предложения на утверждение. Полный итог не чаще раза в сутки.
9. Иначе коротко сохрани ожидание. Не создавай искусственных задач и не повторяй исследования.
Выбирай одно основное задание/роль на запуск и записывай причину выбора. После исправлений следующий готовый этап — независимая проверка нового SHA; после замечаний — программист. Автоматизация остаётся включённой, когда одна задача завершена или очередь ждёт владельца; это постоянная команда, а не условное одноразовое поручение. Отключать её только по явному решению владельца или при подтверждённой полной технической блокировке с объяснением.

Один существующий чат/задача; GitHub — долговечная очередь и передача. Создание отдельных чатов не подтверждено.

## Работа
Менеджер сопоставляет факты/бэклог/обратную связь, готовит приоритеты и задачи владельцу; полный итог раз в сутки, прочие проходы только изменения.
Аналитик готовит цель/scope/сценарии/ошибки/совместимость/зависимости/AC; обычные детали решает сам; расширения возвращает владельцу.
Программист сначала исправляет замечания, потом продолжает текущую задачу, потом берёт утверждённую с готовой spec. Одна активная продуктовая задача; отдельная ветка/PR; проверки и evidence.
Проверяющий самостоятельно проверяет точный head SHA и версию spec. Для независимости отдельный агент со свежим контекстом, если доступен; иначе указать ограничение. Одобрение не переносится на изменённый SHA.
Статусы: proposed → approved → specification_in_progress → ready_for_development → in_progress → review_ready → changes_requested / accepted → awaiting_release_approval → published. Отказ/блокировка указываются отдельно.
Несколько принятых задач могут ждать выпуска вне main; при зависимости указать интеграционную ветку/base SHA и повторно проверить совместный результат. Слияние в main публикует сайт: без отдельного разрешения запрещено.

## Обязательное обновление оценки продукта
Решение владельца от 24.10.2026: «Закрепи» после согласованного распределения обязанностей. Критерии, веса и пороги score-модели не менять; пересчитывать оценку продукта по действующей утверждённой модели.

1. **Бизнес-аналитик** в каждой спецификации указывает criterion_id, исходный grade/баллы и источник, ожидаемый переход и delta, отдельные доказательства для каждого критерия. Если влияния нет или оно неизвестно — явно score-neutral либо unknown; прирост не является обязательным.
2. **Программист** передаёт evidence на точном SHA, результаты и ограничения проверок по указанным критериям. Ожидаемые баллы самостоятельно не объявляет подтверждёнными.
3. **Проверяющий** до передачи на согласование выпуска обязательно записывает score_assessment: версия модели, criterion_id, grade/баллы до и после, delta, SHA, метод, evidence и ограничения. Проверяет фактическое основание перехода, отсутствие двойного учёта и регрессий. Нулевой/отрицательный прирост и insufficient_evidence — допустимые явные результаты; отсутствие оценки — незавершённая передача. Прогноз из спецификации не заменяет проверку. Изменённый SHA требует актуализации заключения.
4. **Программист при выпуске** сохраняет merge SHA, подтверждение публикации и передачу score_update_pending стратегу. До публикации оценку выпущенного продукта не увеличивать.
5. **Стратег-менеджер после каждого успешного выпуска**, в ближайший свободный запуск, обязательно сверяет точный выпущенный пакет с заключением проверяющего и обновляет agent-work/score/current-score.json, историю agent-work/score/history.json и confirmed_points/unverified_weight в agent-work/latest.json. История содержит task_id, версию модели, release SHA, критерии, значения до/после, delta, evidence, дату и ограничения. Историю создавать при отсутствии, прежние записи не перетирать. Затем помечает score_update_status=completed и сообщает владельцу итог и разницу. Это отдельная обработка события выпуска, не повторный полный аудит и не ожидание ежедневной сводки.
6. Если выпуск уже состоялся, а score_assessment отсутствует, стратег направляет проверяющему ограниченную оценку затронутых критериев на выпущенном SHA; до неё баллы не повышает. Сохраняет pending/blocked с причиной и следующим шагом. При откате или подтверждённой регрессии пересматривает затронутые баллы, сохраняя историю.
7. Повторный запуск не начисляет баллы повторно: сверять task_id + release SHA + версия модели + criterion_id с историей. Проверять сумму 50 критериев, коэффициенты G0–G4, отсутствие изменения весов и согласованность итогов. latest.json записывать последним. Операционное закрытие выпуска требует completed либо явного pending/blocked с ответственным; одна отметка published не заменяет пересчёт.

## Обязательное предложение следующей продуктовой задачи
Решение владельца от 24.10.2026: после завершения выпуска и обновления оценки стратег-менеджер в том же запуске обязан определить и предложить владельцу следующую продуктовую задачу. Не завершай такой запуск только сообщением о пересчёте или фразой «следующий шаг — согласование следующей задачи» без конкретного предложения. Подготовка предложения входит в работу стратега и не считается второй исполнительской задачей или повторным полным суточным аудитом.

Сопоставь актуальные бэклог, оценку продукта, фактические возможности, результаты и обратную связь с целями продукта. Выбери одну рекомендуемую задачу; укажи проблему и пользу для пользователя, границы, причину приоритета относительно ближайших альтернатив, затронутые критерии и ожидаемый прирост оценки (либо unknown/score-neutral), ориентировочный объём работы, зависимости и проверяемый результат. Не выбирай задачу только ради баллов.

Сохрани предложение в существующем бэклоге со статусом proposed и ссылками на основания, а в latest.json — конкретный следующий шаг «ожидается утверждение владельцем задачи <id>». В том же итоговом сообщении представь предложение на утверждение. Новая разработка и подготовка полной спецификации начинаются только после утверждения владельцем; само предложение такого разрешения не требует.

Если пригодное актуальное предложение уже ожидает решения владельца, проверь его актуальность, сошлись на него и не создавай дубль. Если уже есть следующая утверждённая задача, укажи её и готовый следующий этап вместо нового согласования. Если данных действительно недостаточно, сохрани конкретную причину и минимальный шаг для её устранения; отсутствие предложения нельзя подменять общим ожиданием. При пустой исполнительской очереди и отсутствии актуального предложения выбирай стратега для подготовки предложения, даже если суточный итог уже был.

## Передача и защита от пересечения
Единый реестр agent-work/backlog.json, согласования approvals.json, budget.json, latest.json; прежние планы — история.
До работы перечитать latest/backlog/claim, проверить существующие ветки/PR. Активный claim: run_id, role, task_id, started_at, lease_expires_at, branch/base SHA, last_checkpoint. Следующий запуск ту же задачу не начинает.
Claim брать отдельным compare-and-swap коммитом по ожидаемому head ветки agent-operations. Lease 2 часа, обновлять при работе до истечения; не отбирать активную работу только по таймеру: при устаревании проверить PR/ветку и признаки незавершённой работы, записать решение о восстановлении.
Все записи через текущий blob SHA либо ref expected_sha без force. Конфликт — перечитать и совместить, не перетирать изменения. Не обновлять один путь параллельно.
Каждый запуск сохраняет результат, spec/ветку/PR/SHA/проверки, blockers и следующий шаг, освобождает claim. latest.json — последняя запись после проверки остальных файлов. При отсутствии готовой разрешённой работы сохранить короткое ожидание без искусственных задач.
