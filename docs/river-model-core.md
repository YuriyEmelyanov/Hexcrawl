Статус: действующее описание API; результаты первого этапа — исторические.
[Полная прежняя редакция](archive/2026-10-22/river-model-core.md).

Реализация: `src/riverModel/core.ts`. Основание: [спецификация v0.3](river-model.md)
и [аудит](river-model-audit.md). Числовой слой подключён к App.tsx;
[интеграция, проверки и ограничения](river-model-integration.md).
Ниже сохранено описание самостоятельного API ядра и проверки первого этапа.

## Что реализовано

- `confluenceOutputs(a, b)` и `confluenceInputs(output, tributary)` используют
  одну симметричную таблицу. Неверные значения не дают допустимых решений.
- `minimumLakeHexes(inputs, outputs)` рассчитывает требуемую площадь:
  исток — максимум из 1 и F−1; проточное озеро — максимум из 1 и разницы сумм
  по модулю; бессточное — сумма входов. Минимум 1 нужен для существования озера;
  обычный исток без озера задаётся отдельным узлом source.
- `lakeAllows` сравнивает требование с фактическим количеством гексов,
  не с запрошенным размером будущего озера.
- `validateRiverNetwork(unknown)` проверяет формат, значения F=1…5,
  принадлежность/высоты секторов, узлы, направленность и правила баланса.
  Ошибки содержат rule, code, nodeId или edgeId и пояснение.
- `solveRiverNetwork(unknown, {maxStates})` решает прямую и обратную задачи
  на одной сети. Заданные fullness — жёсткие условия, отсутствие fullness
  означает неизвестное значение. Входные данные не изменяются.

## Входная сеть

Узлы: source, continuation, confluence, lake, sea, open.
Каждое ребро имеет id, from, to, regionId, height и необязательное fullness.
height относится к региону сектора, а не выбирается по одному из соседних гексов.
Для одного regionId противоречащие высоты отклоняются.

Continuation соединяет два сектора без изменения F; так представляются
границы регионов/высот. Open — один открытый конец любого направления,
не настоящий исток. Source имеет один выход F=1. Confluence имеет два входа
и один выход. Sea принимает реки и не имеет выходов. Lake хранит положительный
целый lakeHexCount; при нескольких входах/выходах площадь учитывается один раз.

Озеро без входов и с несколькими выходами не определено отдельно правилами
истока. Такое представление отклоняется как неподдержанная степень узла,
без выдуманного распределения базовой единицы воды. Проточное озеро с несколькими
выходами поддерживается по согласованной сумме.
Направленные циклы, висячие ссылки и повторяющиеся ID отклоняются.

## Алгоритм и выбор результата

1. Для неизвестного ребра начальные варианты 1…5; для известного — одно значение.
2. Ограничения узлов сокращают варианты до неподвижной точки в обе стороны.
   Для озёр считаются точные достижимые суммы, включая возможные пропуски.
3. Если остаются неоднозначности, выполняется поиск с ограничением числа состояний.
4. Среди полных допустимых решений сначала максимизируется число увеличений
   на слияниях высоты 1, затем минимизируется суммарное отклонение секторов
   от предпочтения высоты (1 для высоты 3, 2 для высоты 2, диапазон 3–5 для высоты 1).
   Эта явная политика обеспечивает обратный выбор 2+1→3 вместо 3+1→3, когда
   верхний участок ещё не задан. Фиксированные значения всегда выше предпочтений.
5. Равные оценки разрешаются по каноническому порядку ID рёбер и значений.
   В числовом ядре нет случайности. Подключённый адаптер геометрии описан в
   [river-model-integration.md](river-model-integration.md); общего пользовательского
   seed географии пока нет. Порядок массивов входной сети не меняет выбранный результат.

Политика оценки — конкретный способ реализации предпочтений, а не новое
ограничение допустимости. Валидатор принимает и менее предпочтительное,
но допустимое решение, например уже существующий выход 3 после входов 3 и 2.

Результаты:

- solved — полный допустимый результат и его оценка;
- invalid — неверный/неподдерживаемый формат сети;
- unsatisfiable — доказанное отсутствие допустимого назначения при данных условиях;
- limit — поиск исчерпал бюджет (по умолчанию 50 000 состояний).

Limit не означает невозможность сети. Частичный или неоптимальный найденный
вариант в этом случае не выдаётся как окончательное решение. Бюджет считает
состояния поиска, не миллисекунды. Из результатов числовых тестов нельзя вывести производительность больших карт.
Подключённый адаптер передаёт затронутые компоненты с фиксированными старыми
участками; его бюджеты и ограничения приведены в [интеграции](river-model-integration.md).

## Проверки и предел покрытия

`test/riverModel.test.mjs` проверяет числовой API: таблицы слияний и обратный
подбор, площади озёр, источники, многорусельный баланс, порядок входных массивов,
ошибки формата/F/циклы, лимит поиска и неизменность входа. Общая команда —
`npm run check`; реальные обработчики и браузер дополнительно покрывают адаптер.

Историческая матрица первого этапа EX-01…24, 20 новых тестов и прежние итоги
57/77 сохранены [в архиве](archive/2026-10-22/river-model-core.md).
Они не означают актуальное число тестов или отсутствие интеграции сегодня.
Регрессии AUD-01…04 через настоящий обработчик, размещение озёр, границы
сохранности и браузерная проверка описаны в [отчёте подключения](river-model-integration.md).

Числовой валидатор принимает переданную сеть; геометрические пересечения, море
у источника и фактическую площадь озера должен корректно представить адаптер.
Автоматическая миграция всех старых дефектов карты из этого API не следует.
Конечный набор тестов не доказывает выполнения всех правил при любой геометрии.
