Технические задачи
Актуализировано 03.10.2026 по main, коммит 65f4bd1.
Проверка исходного состояния: npm run check проходит — ошибок TypeScript нет, 103 теста успешны, production build собирается. Проверки типов, тесты и браузерные сценарии уже включены в CI и блокируют публикацию при ошибке.
[0.1.3] Зафиксировать зависимости
Добавить package-lock.json в репозиторий. В workflow проверки и публикации заменить npm install на npm ci.
Готово: чистая установка по lock-файлу и npm run check проходят на Node.js 24; CI использует npm ci.
Причина: повторная сборка одного коммита должна использовать одинаковые версии зависимостей.
[0.1.3] Разделить штатные отказы генерации и программные ошибки
Проверить обработку исключений в построении рек и добавлении региона. Сейчас неожиданные исключения могут превращаться в обычный отказ генерации или создание урочища.
Штатная несовместимость ограничений должна возвращать понятную причину отказа и использовать предусмотренные повторные попытки и урочище. Неожиданная программная ошибка должна прекращать действие, оставлять прежнюю карту целой и формировать диагностику.
Добавить проверки обоих случаев: штатный отказ и искусственно вызванная программная ошибка. Проверять также историю и возможность продолжить работу после сбоя.
Готово: программный сбой нельзя принять за успешную генерацию; неудачное действие не меняет карту и историю; штатный переход к урочищу работает.
Причина: перед исправлением гидрологии необходимо видеть настоящие причины неудач.
Упорядочить диагностику генерации
Ввести отключаемое подробное логирование. Убрать безусловные отладочные console.log из обычного режима; сохранить сообщения об ошибках и существенных отказах. Существующий профайлер сохранить.
Для неудачного действия записывать версию алгоритма, параметры генерации, якорный гекс, номер попытки и причину отказа. После внедрения общего генератора случайных чисел включить его состояние.
Раздельно учитывать штатное создание урочища, исчерпание попыток и программный сбой.
Готово: по диагностике можно установить причину неудачи; обычное использование не создаёт поток подробных отладочных сообщений.
Причина: успешное появление региона само по себе не показывает качество работы генератора.
Сделать генерацию карты воспроизводимой
Ввести единый генератор случайных чисел для географии, рек, озёр, дорог и случайных элементов карты. Заменить прямые обращения к Math.random в этих операциях.
Сохранять начальный seed, текущее состояние генератора и версию алгоритма. История и отмена должны восстанавливать соответствующее состояние генератора.
Сохранить существующую независимую генерацию названий. Предусмотреть загрузку старых карт без новых полей.
Проверить два сценария:
• одинаковые seed, параметры и последовательность действий дают одинаковую карту;
• после сохранения и загрузки следующее действие даёт тот же результат, что и без перезагрузки.
Готово: оба сценария воспроизводятся на одной версии алгоритма; старые карты загружаются; отмена восстанавливает карту и состояние случайности.
Причина: ошибку должно быть возможно повторить, а изменение алгоритма — сравнить на одинаковых условиях. Одного seed без состояния и последовательности действий недостаточно.
Расширить проверки последовательной генерации
Использовать существующий тестовый механизм настоящего обработчика генерации. Текущие тесты сохранить.
Добавить более длинные последовательности расширения карты с разными размерами, высотами, освоенностью и режимами побережья. Проверять после каждого действия:
• корректность речной сети по действующим RIV-правилам;
• сохранность ранее созданных участков;
• связность регионов и отсутствие пересечений;
• непрерывность дорог и корректность переправ;
• сохранение, загрузку и отмену.
Отдельно проверять числовую корректность рек и геометрию русел. Допустимая полноводность не доказывает правдоподобность маршрута.
Сохранять отчёт: число выполненных действий, программные сбои, нарушения правил, доля урочищ и время генерации. Каждый найденный дефект превращать в отдельный воспроизводимый регрессионный пример.
Готово: прогон повторяется, нарушения сопровождаются примером для воспроизведения, результаты зафиксированы в репозитории. Конечный успешный прогон не считается доказательством отсутствия любых ошибок.
Причина: основные риски проявляются при взаимодействии нескольких регионов, рек и побережья.

Готово: выделенная часть получает явные входные данные и возвращает результат; не зависит от React; проверяется отдельно и через настоящий обработчик приложения.
Причина: это упростит исправление рек и проверку взаимодействия с рельефом, озёрами и морем.

Правила выполнения
• Перед изменением генерации читать соответствующие спецификации в docs/.
• Не менять бизнес-правила ради прохождения тестов.
• Не смешивать исправление алгоритма с широким рефакторингом.
• Перед передачей изменений выполнять npm run check на Node.js 24.
• Для изменений генерации после сборки выполнять npm run test:browser.
• Проверять старые сохранения, сохранность существующей карты и отмену.
• Обновлять спецификацию при изменении поведения.
• Недоступную или незавершённую проверку явно указывать в результате работы.

Постоянные векторы развития HexCrawl.ru

Готовый сценарий
Давать пользователю законченный результат, ради которого он приходит в HexCrawl.
Контрольный вопрос: появилась ли новая причина использовать HexCrawl?
География
Постоянно улучшать естественность, качество и разнообразие карты.
Контрольный вопрос: стала ли сама карта лучше?
Кастомизация
Давать пользователю больше контроля над результатом генерации.
Контрольный вопрос: может ли пользователь получить именно нужную ему карту?
Игровой инструментарий
Превращать карту в инструмент подготовки и ведения игры.
Контрольный вопрос: стало ли мастеру полезнее пользоваться картой за столом?
HEALTH
Движок / архитектура
Сохранять возможность быстро и безопасно развивать продукт.
Контрольный вопрос: не делает ли сегодняшняя разработка следующий шаг дороже и опаснее?
Баги / надёжность
Не допускать деградации уже работающих функций.
Контрольный вопрос: можно ли доверять тому, что уже реализовано?
Правило: каждый релиз имеет один главный пользовательский результат. Шесть векторов — не обязательный чек-лист релиза, а контроль баланса развития продукта на горизонте нескольких версий.
