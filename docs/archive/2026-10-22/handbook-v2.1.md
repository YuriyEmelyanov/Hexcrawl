0. Как пользоваться handbook

• Каждая задача должна быть привязана к одному критерию Scorecard или явно помечена как score-neutral.

• Points начисляются только при переходе между G0, G1, G2, G3 и G4.

• Количество функций, строк кода, иконок или биомов само по себе не является value.

• Один результат нельзя посчитать дважды. Например, мосты входят в критерий дорог, а не создают отдельные points.

• Grade повышается только при наличии evidence: теста, benchmark, аналитики или пользовательского исследования.

• Каждый релиз имеет minimum score gate. Релиз не считается завершённым, пока gate не достигнут.

• После релиза фиксируются baseline commit, новые grades, evidence и обновлённый gap до 1000.

Главное продуктовое правило: сначала повышаем доказанный grade, затем расширяем scope.

0.1 Формула value

points = max value критерия × коэффициент grade
G0 = 0.00 | G1 = 0.25 | G2 = 0.50 | G3 = 0.75 | G4 = 1.00

• G1: прототип работает в отдельных случаях.

• G2: функция работает в обычных сценариях.

• G3: есть автотесты, обработка ошибок и подтверждение пользователями.

• G4: выполнен числовой критерий и доказано превосходство над аналогами.

0.2 Что означает 1000

• Все 50 критериев Scorecard имеют grade G4.

• Все числовые benchmark и исследования сохранены и воспроизводимы.

• Нет открытых critical defects для карты, сохранения и кампании.

• Результат подтверждён не только владельцем продукта.

2.1 Правило релизных gate

• Minimum score — обязательный порог, а не прогноз.

• Delta считается относительно предыдущего gate.

• Scope можно сократить, но minimum score нельзя заменить количеством выпущенных функций.

• Если новая функция не меняет grade, она выпускается только при небольшом cost или стратегической необходимости.

• Начиная с 0.2, ни один релиз не принимается без migration test и regression report.

• Начиная с 0.3, каждый релиз проверяется реальной игровой подготовкой.

• Начиная с 0.9, score повышается только вместе с внешним evidence.

2.2 Что нельзя начинать раньше времени

До gate | Не начинать как основной поток | Почему

350 | Фракции, угрозы, длинные описания гексов | Нестабильное ядро заставит переписывать контент.

500 | Массовую библиотеку из сотен POI | Нет устойчивых ID, pack format и granular reroll.

650 | Глубокую симуляцию мира | Сначала доказать, что отдельный гекс готов к игре.

780 | Три и более RPG-адаптера | Сначала стабилизировать системно-нейтральную модель.

850 | Агрессивное заявление «лучший в мире» | До внешнего benchmark это только маркетинг.

5. Архитектура, необходимая для 1000

5.1 Слои

Space Grid
  → Geography
    → Infrastructure
      → World
        → Campaign
          → Content
            → Presentation

Слой | Сущности | Запрещённая связка

Space Grid | hex, vertex, edge, adjacency | UI style не входит в координаты

Geography | biome, height, river, lake, sea, coast | Река не хранится как hasRiver=true

Infrastructure | road, trail, crossing, settlement | Мост не является только иконкой

World | faction, territory, culture | Не хранить в React state как текст

Campaign | time, threat, project, entity state | Не смешивать с неизменным определением мира

Content | POI, NPC, rumor, reward | Слух обязан ссылаться на entity ID

Presentation | tile, icon, label, visibility, zoom | Замена тайлсета не меняет мир

5.2 Три разных вида данных

Уровень | Пример | Зачем разделять

World definition | Руина расположена в hex_0412; её населяют культисты. | Постоянная истина мира.

Campaign state | Вход обрушен; культ ослаблен; день 18. | Изменения конкретной кампании.

Player knowledge | Игроки знают «старую башню» примерно к северу. | Туман войны, ошибки и ложные сведения.

6. Операционная модель разработки

6.1 Безопасный рефакторинг

1. Сначала regression test на текущее поведение.

2. Затем извлечение типа или функции без изменения логики.

3. Изменение сигнатуры и изменение алгоритма — разные PR.

4. Каждый PR выполняет npm run check.

5. При изменении snapshot — migration test и обратная совместимость.

6. При изменении географии — массовый прогон и отчёт по инвариантам.

6.3 Definition of Done любой задачи

• Указаны step, criterion, current grade, target grade и потенциальный delta.

• Есть пользовательский результат и числовой критерий.

• Есть тесты инвариантов и ручной smoke-сценарий.

• Старое сохранение открывается или добавлена миграция.

• Analytics/evidence сохраняются в репозитории.

• Документация и ADR обновлены при изменении архитектуры.

• PR решает одну задачу и имеет rollback path.

12.3 Процесс пересчёта

1. Зафиксировать baseline commit.

2. Выбрать только изменившиеся критерии.

3. Приложить evidence.

4. Повысить grade только на G0/G1/G2/G3/G4.

5. Пересчитать points и release gate.

6. Обновить handbook, scorecard и release notes.

12.4 Запреты

• Не повышать grade по плану или обещанию.

• Не учитывать один результат в нескольких критериях без независимого evidence.

• Не менять критерии Scorecard, чтобы улучшить текущий score.

• Не удалять benchmark, в котором продукт проиграл.

• Не выпускать migration-breaking change без конвертера.

15.1 Следующее действие владельца продукта

1. Создать в GitHub milestone `M350 / 0.1.2`.

2. Каждой открытой задаче назначить Score step/criterion и потенциальный delta.

3. Добавить задачи `Master seed` и `npm run check` в 0.1.2.

4. Создать папку `docs/score/evidence`.

5. Провести baseline 10 000 генераций и сохранить отчёт.

6. Не начинать кампанийный слой до прохождения gate 500.

Текущий путь: 262,5 → 350. Главный риск — не нехватка функций, а недоказанная надёжность и архитектура, которая затруднит безопасное редактирование.
