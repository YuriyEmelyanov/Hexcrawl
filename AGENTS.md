# Работа над HexCrawl

Перед изменением генерации прочитай README.md и соответствующую спецификацию в docs/.
Для задачи №1 обязательна docs/region-generation.md.
Перед изменением рек обязательно прочитай docs/river-model.md. Учитывай статус
правил и открытые вопросы; изменение поведения сопровождай обновлением
связанных RIV-правил, примеров и тестов в том же PR. Отличай действующие правила от
запланированных изменений; не изменяй бизнес-правила ради прохождения тестов.

Перед изменением дорог прочитай docs/road-model.md и docs/road-model-audit.md.
Сохраняй ROAD-правила; гипотезы аудита не выдавай за подтверждённые ошибки.

- Сначала воспроизведи ошибку тестом или сохранением с точными шагами.
- Исправление включает проверку результата через настоящий обработчик генерации.
- Проверяй смежные ветки, существующие регионы, реки, сохранение и отмену.
- Перед передачей изменений выполни `npm run check` (Node.js 24).
- Для изменений генерации дополнительно выполни `npm run test:browser` после сборки.
- При изменении поведения обнови спецификацию и результаты проверки в том же PR.
- Не смешивай изменение алгоритмов с широким рефакторингом.
- Не называй конечный набор успешных прогонов доказательством отсутствия любых ошибок.
- Если проверка или публикация недоступна, явно укажи незавершённый шаг.

Основной сайт публикуется GitHub Pages workflow из main. Сохраняй этот способ
публикации; перенос на другое размещение требует отдельной задачи.

## Обязательная проверка автоматизации для каждой роли
Решение владельца от 25.10.2026: «Уже второй раз самостоятельно отключается. Запиши в инструкции каждому агенту проверять, что не отключено».
Применяется к стратегу-менеджеру, бизнес-аналитику, программисту и проверяющему, включая запуск вручную.

1. В начале работы и непосредственно перед завершением запуска проверь через automations.peek фактический is_enabled задачи «Команда HexCrawl», jawbone_id=6ad9c2426c7481919bb9f3d2b289e9b9. Значение schedule_status в GitHub не заменяет эту проверку.
2. Если is_enabled=false, проверь актуальные решения владельца и зарегистрированную причину остановки. При отсутствии явного поручения владельца об отключении или подтверждённой полной технической блокировки включи эту же задачу через automations.update(is_enabled=true), затем повторным peek подтверди результат. Это восстановление уже разрешено владельцем; повторного согласования не требуется. Новую автоматизацию не создавай, расписание и остальные инструкции не меняй.
3. Завершение задачи, принятие PR, выпуск, ожидание согласования, пустая очередь, завершение текущего запуска, неизвестный бюджет и временные ошибки сервиса не являются основанием отключить постоянную команду.
4. Если отключение разрешено действующим решением владельца либо необходимо из-за подтверждённой полной технической блокировки, сначала сохрани конкретное основание и evidence в GitHub; не включай задачу вопреки актуальному решению владельца.
5. В результате запуска сохрани automation_health: ID, время и фактический статус проверок start/end, выполненное восстановление и ошибки. Затем обнови latest.json последним. Не перетирай чужой claim/результат. При недоступности инструмента явно укажи unchecked/error, не объявляй состояние enabled без подтверждения и сообщи владельцу.
6. Проверка относится к доступному моменту времени: она не гарантирует, что сервис не отключит задачу после завершения запуска. Причину отключения не выдумывай.
